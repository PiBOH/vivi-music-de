### Android ↔ Desktop sync
- [x] **The seek/duration fix was read back from a live paired session (done 28 Sep, session `20260928-185622`, DE 1.54.x).** The desktop's own positions climb again — `send [tick/state] … pos=179090ms, 184100ms, 189110ms, 194130ms, …` (+5010 ms per ~5 s tick, the normal cadence) instead of freezing on one value — a backward seek lands (`applying peer USER SEEK: -> 90027ms (was 213886ms)`, then `-> 26594ms (was 172101ms)`) and the follow-up ticks are ordinary forward drift (`90027ms -> 91080ms`), not a restart to zero. The duration is real too: `lyrics.log` reads `duration=227s` where the same fetch used to say `duration=unknown`. **Watch:** the failure signature is still a single repeated `pos=` value with a fresh `audio output` line every ~5 s in `playback.log`.
- [x] **Every seek bar was dead and the track read 0:00 (done 28 Sep, 1.54.0).** Session `20260928-175425` shows the desktop frozen at `pos=237ms` while the phone played: each 5 s drift tick logged `drift catch-up: 237ms -> …`, the player restarted from the top every time (`playback.log` prints a fresh `audio output` + `audio integrity` pair at the same cadence) and the bar showed `0:00`. `PlayerState.durationMs` was 0, and `seekInternal` clamps with `coerceIn(0L, durationMs)` — so every seek became "seek to 0". Two holes fed the zero: adopting the peer's queue refreshed the queue and the index but not the duration, and the desktop's own pushed queue carried no `TrackRef.durationMs` at all. The adopted length is now taken over, the desktop sends the lengths it has, and a seek is clamped only against a *known* length. **Watch:** in `sync.log` a drift catch-up now has to be followed by a `send … pos=` that keeps moving, and `playback.log` must not print an `audio output` line every ~5 s (that was the restart loop).
- [x] **"Disconnect" left the pair behind (done 28 Sep, 1.54.0).** The relay Disconnect only closed the socket: the pair id stayed on both sides, the peer kept listing a desktop that could not come back, and the user had to press Unpair by hand. - [x] **The native OS volume could not be kept out of the sync (done 28 Sep, 1.54.0, new option).** The in-app slider and the native OS/`STREAM_MUSIC` volume were gated by one switch, so turning "Sync VIVI volume" off also stopped the in-app mirror and leaving it on meant the two machines' master volumes chased each other. ### Android ↔ Desktop sync (older items)
- [x] **A track skipped on the phone changed the song on the desktop but did not start it (done 27 Sep, 1.53.34).** A skip arrives as `playing=false resolving=true` (the skip rebuffers the new stream, and the phone's `isPlaying` reads false while the media item is swapped in), so the desktop adopted the new queue *paused*; the later `playing=true` ticks all landed while the desktop was still resolving its own new stream and were deferred, and the deferral re-applies a position, not an intent. The skip's intent now survives the rebuffer: a track change that arrives while the peer is resolving inherits the peer's last clear intent, and `track change applied from the peer` prints `startPlaying=true` (the phone's own skip always forces `playWhenReady = true`). **Watch:** after a skip, the log has to show `startPlaying=true` on the desktop and then `audio started on this device` without a play press; a `startPlaying=false` on a skip means the snapshot lost the `resolving` flag.
- [x] **A user seek was dropped by the receiver's own "peer is resolving" hold (done 27 Sep, 1.53.33).** Both receivers checked `isResolving` before `userSeek`; a phone seek always carries `resolving=true` (the seek makes the phone rebuffer), so it fell into the hold and the follow-up `seek=false` tick is a forward-only catch-up — a backward seek had no way back. `userSeek` is now checked first on both sides, the `recv:` line also prints the local position/play/resolving, and a snapshot deferred because *we* are resolving says so explicitly. **Watch:** `applying peer USER SEEK` after a backward drag now has to appear on whichever device did not move, and `deferred (our own stream is resolving)` has to be followed by a `stream ready — re-applying` line, never nothing.
- [x] **The seek and track-start fixes were read back from a live paired session (done 27 Sep, session `20260927-152955`).** A backward seek is applied (`applying peer USER SEEK: -> 12195ms (was 211950ms)` at 15:38:16.5, `-> 0ms` at 15:38:45.5) and every deferred snapshot is followed by its verdict: `deferred (our own stream is resolving)` at 15:38:48.136 is answered by `stream ready — re-applying the snapshot received while buffering: -> 10257ms playing=true` at 15:38:58.406, never by nothing. **What the same log then exposed:** the desktop only recovered because the peer's next `playing=true` tick arrived, and on this phone-hotspot link its own resolve took 10 s, so the skipped track stayed silent that long — which is what 1.53.34 fixes at the source (see the item above).

### Audio (Windows)
- [x] **The device was being started under-primed, and that is the audible gap (done 26 Sep, 1.53.28).** The Windows sessions pair `audio output primed: device started with 139ms …` with `audio writer stalled: 1170ms for one pass with only 2ms of it inside the device write (queue 7987ms, cushion 139ms)`: a 139 ms ring drains in 139 ms, so the device went silent with 8 s of PCM queued. The prime now gives up on the 500 ms target only when the queue is empty (nothing left to wait for) or after a 3 s hard bound, not on a 500 ms wall clock. **Watch the next export for `reached the 500ms target` on the normal starts:** that is the line that says the prime is fixed instead of merely bounded.
- [ ] **A scheduling freeze longer than ~1 s is still audible.** Java Sound's device ring is hard-capped at 1000 ms there (measured: any request above 1 s is granted exactly 176400 bytes; macOS grants 4 s) and MMCSS now covers the ~1 s range. Beyond that it means a native WASAPI render path (event-driven, own ring) or a bigger ring in the current backend. **Do not start without a measurement:** the logs must first show the writer frozen *outside* `out.write()`.

### Audio (macOS, #3)
- [ ] **The 1 s cushion is retirable once this is measured, and 1.53.25 is what measures it.** The cushion is a legitimate pre-roll, but its *value* was raised around a writer pass that took 325-556 ms, and a buffer sized around a hiccup hides the hiccup instead of removing it. Every pass is timed from now on (the opening one, the first 30 / first 4 s in full, every pass over 200 ms after that, with `audio writer passes: … none of them over 200ms` in the 10 s device check and per track in `audio integrity`). **The decision rule:** `none of them slow outside the device write` after a few sessions means the slow pass really was the opening one, so the target can come back down to 0.3 s; a count that keeps growing means the thread is being taken off the CPU and the fix is its priority and allocation behaviour (`AudioThreadBoost`, no allocation on that path) — not another cushion. **Do not raise the cushion again without this line**, or the workaround becomes permanent by accident.
- [x] **The 1.53.20 export was read session by session (done 25 Sep).** It contains no playback defect: in its sixteen 1.53.20 sessions, 0 `sample-table overlaps`, 0 `device stalls`, 0 `cushion low`, 0 `starved`, and `audio device check` at 99-100 % on a 4000 ms ring. Its four 20 Sep sessions are leftovers from an older build (they still carry the removed `sample table discontinuity` message) and are the only place a `device stall` appears — every one of them spans a pause. The three `audio writer stalled` lines are the *pre-start* pass of a track start, logged 0-2 ms after their own `audio output primed`; that pass runs before `out.start()` and cannot drain the ring. The analysis and the marker table now live in §10 of `AGENTS.md`.
- [ ] **What the export does prove is start latency, and it is not in the writer.** Press play → first sound is 0.4-1.2 s for a cached track and 2.2-4.1 s over the network, of which `resolving` alone is 1608-2718 ms; the device ring is 99-100 % in every window, so none of it is an underrun. **Next step if the jump is still audible:** a fresh export from a build ≥ 1.53.26 read with the §10 table, and if it is clean again the target moves to the `resolving` stage (one player request per track, no prefetch of the *next* track's stream URL) — not to the output pipeline.
- [ ] **The cushion is now set by measurement, and the per-pass timing of 1.53.25 is what retires it.** All 30 starts in the 1.53.20 export were primed with 139 ms, 278 ms or 417 ms against a 1000 ms target, because a 400 ms wall-clock plateau (removed in 1.53.26) inferred "the ring is full" from "the producer went quiet" — a `SourceDataLine` that has never been started feeds the writer in bursts. A short write is now the only thing that concludes the ring is full. **The decision rule stands:** `audio writer passes: … none of them slow outside the device write` after a few sessions means the target can come back down to 0.3 s; a count that keeps growing means the thread is being taken off the CPU and the fix is its priority and allocation behaviour (`AudioThreadBoost`, no allocation on that path) — not another cushion. **Do not raise the cushion again without this line.**
